# 專案 AGENTS.md 初始化與審查標準

本文件供 agent 初始化、審查或修改其他專案的 `AGENTS.md` 時使用。它是工作的參考標準，不是直接複製到每個專案的範本，也不要求每次任務都載入。

## 來源與適用邊界

已完整閱讀的主要來源：[HumanLayer — Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)，發布日期 2025-11-25。作者明確表示文章也適用於 `AGENTS.md`。

本文採用的文章原則：以專案用途、結構與工作方式完成入門；常駐指令精簡且普遍適用；細節按需揭露；引用權威來源而非複製；格式規則交給工具；避免未經思考的自動生成。

下列作業程序、檢查表與驗收方式是依這些原則制定的使用標準，不是文章原文或作者規定。文章提到的行數、指令數與特定工具行為不作為跨模型、跨平台的硬性門檻。

- **全域規則**：使用者跨專案的行為偏好、授權邊界與協作約束。存放本標準的 `agentic-coding` repo 根目錄 `AGENTS.md` 用於這個角色，不因缺少該 repo 目錄圖而判定不合格；這不表示待初始化的其他 repo 根文件也是全域規則。
- **專案規則**：讓 agent 能正確開始維護特定 repo 的必要知識，是本標準的審查對象。
- **局部規則與流程**：只適用特定目錄、技術或任務的細節，依目標環境支援的作用域與按需引用機制放置。

不要在專案檔重複整套全域守則，也不要假設目標環境一定載入使用者的全域設定。先確認實際適用的指令；有衝突時指出，不靜默覆蓋。其他 AGENTS 變體不能只憑檔名就被當成根文件的附錄。

## 一、先從 repo 取得證據

在寫入前，按任務需要檢查：

1. 既有根目錄／局部 `AGENTS.md` 與實際適用的全域規則，辨識哪些內容是手寫的專案知識。
2. README、目錄、套件或工作區設定，確認專案目的、主要元件與責任。
3. package scripts、Makefile、CI、測試與格式工具設定，找出真正的工作入口。
4. 既有架構、開發與操作文件，確認可直接引用的權威來源。
5. 與任務相關的已知限制、生成檔、vendored 內容、執行環境與安裝副作用。

不要為了初始化而讀完整個 repo。排除依賴目錄、建置產物及秘密值；不要從檔名猜用途，或憑慣例杜撰測試命令。遇到會影響正確性的資訊缺口，先查證；仍無法確認才提出具體問題。

## 二、根文件應提供的資訊

| 項目 | 應回答的問題 | 審查依據 |
| --- | --- | --- |
| 專案用途 | 這個專案解決什麼問題，主要交付物是什麼？ | 能與 README、實際入口相互對照 |
| 結構與責任 | agent 應到哪裡找相關程式、測試與文件？ | 只列有助定位的重要目錄，路徑確實存在 |
| 工作方式 | 如何開始開發，以及驗證本次修改？ | 指向實際命令／設定；說明必要工作目錄與前置條件 |
| 關鍵限制 | 不知道哪件事會造成錯誤修改？ | 有具體專案原因，例如勿手改生成檔、特定安裝格式限制 |
| 按需導覽 | 哪類任務需要讀哪份更詳細的文件？ | 每個入口都有明確適用情境，不要求每次全部讀取 |

不強制使用這五個標題。小專案可用少量段落完成；大型專案也不應在根文件展開完整手冊。

## 三、逐條決定保留、移動、刪除或補充

對每條指令問：

- 它是否提供這個專案必要、可查證且不明顯的資訊？若只是通用勸告，優先刪減或留在全域規則。
- 它是否普遍適用？只適用 UI、資料庫、部署、多 worktree 等情境時，保留條件式入口，把細節移到相應文件。
- 它是否重複既有文件或設定？優先指向權威來源，不維護另一份容易過期的副本。
- 它是否能由工具可靠檢查？格式、lint、型別與可機械驗證的約束應指向已有檢查，不要求 agent 用文字規則手動模擬工具。
- 移除後是否會丟失重要的專案限制？不要為了縮短篇幅犧牲必要資訊，也不要擅自移除使用者指定的安全或協作政策。

修改既有檔案時先做內容分類，再提出或套用局部修改。若兩條規則衝突，說明衝突與選擇理由；不能拼湊成一條含糊規則。不要把過去一次失誤自動升格成所有任務的固定流程。

## 四、按需引用與命令的寫法

- 使用「修改安裝清單時，讀……」這類任務導向的入口；避免「任何修改前，先讀所有文件」。
- 優先沿用既有文件。只有細節確實需要獨立維護時才新增文件，不先生成空的 `docs/agents/` 分類樹。
- 指向設定檔、命名章節或必要的程式位置。只有精確行號能增加價值時才附行號，修改時要重新確認。
- 列少量常用、可查證的開發／驗證入口；其他命令指向既有 scripts 或開發文件。不同修改需要不同檢查時，交代選擇方式。
- 區分「已從設定確認存在」與「已實際執行通過」。未執行的命令不可宣稱已驗證；初始化文件不授權部署、資料重設或外部服務寫入。

專案文件不得依賴本標準所在 repo 或臨時參考 checkout 的本機路徑。必要內容應落在目標 repo 的適當位置；公開來源連結可作出處，不應成為每次工作的強制讀取依賴。

## 五、初始化與修改流程

1. **定義範圍**：確認目標是專案規則；說明本次要建立或修正哪些內容。
2. **查證與分類**：依第一節讀取必要證據，找出缺少、重複、過時、作用域錯誤或互相衝突的指令。
3. **編修**：保留有效的專案知識，補用途／地圖／工作入口，把條件式細節移到適當位置。遵守已授權範圍，不順便更改全域守則。
4. **檢查**：核對下方驗收表，檢查 diff；只執行安全、必要且已授權的命令驗證。
5. **交付**：列出新增、刪減與移動的重點、實際檢查結果，以及未確認事項。AI 可以協助編修，但生成結果必須逐條查證，不能將自動掃描結果直接當成完成品。

審查模式只提供 findings 與修改建議；初始化／修改模式才寫檔。不得因審查標準提到某種工具或流程，就自行安裝工具、建立排程或發布修改。

## 六、完成檢查表

- [ ] 新 agent 能知道專案用途、主要責任區域，以及下一個應讀取的位置。
- [ ] 必要工作與驗證入口有 repo 證據；工作目錄、重要前置條件與副作用清楚。
- [ ] 根文件沒有強制每個任務執行不相關的專門流程。
- [ ] 每個詳細文件入口都說明何時需要讀；沒有斷鏈或臨時參考資料夾依賴。
- [ ] 沒有重複整套全域守則、格式規則或已有權威內容；必要的政策沒有被擅自刪除。
- [ ] 既有手寫知識受到保留；衝突、假設與資訊缺口已明列。
- [ ] 沒有為了達到行數目標刪掉重要資訊，也沒有用大量例子或命令填滿根文件。
- [ ] 回報區分靜態查證、實際執行與未驗證事項；沒有把文件檢查宣稱成模型行為改善的實測。

驗收看的是資訊是否正確、必要、容易找到，而不是標題數、字數或檔案數。
