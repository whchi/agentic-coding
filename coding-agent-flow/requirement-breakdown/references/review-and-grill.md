# Grill 協議與 Review checklist

Step 1（釐清並定 Goal）與 Step 3（Review）共用同一套 grill 協議。協議本體是 `grilling` 與 `grill-with-docs` 兩個 skill，**這裡不複製它們的內容**，只寫拆解流程要加的規則，避免兩邊漂移。

## 選哪個 skill

| 情況 | 用 |
|---|---|
| 預設 | `grilling` |
| 主題有術語爭議（同詞多義、同義多詞）、有既有 docs／ADR／code 要對照、決策需要留下長期紀錄 | `grill-with-docs` |

`grill-with-docs` 預設把 `CONTEXT.md`、`docs/adr/` 放在 repo 根目錄；本流程是「一個主題一個目錄」（位置見 SKILL.md），所以改放 `<主題>/CONTEXT.md`、`<主題>/docs/adr/`。兩個主題的術語開始互相引用時再加根目錄的 `CONTEXT-MAP.md`。ADR 照它的三條件（難回頭、不看脈絡會覺得意外、有真實取捨）才開；共同前提裡寫得下的規則不必升級成 ADR。

## 拆解流程對 grill 加的規則

- **每題附建議答案，等使用者回答。** 提問節奏照所選 skill（`grilling` 一輪問完當下可問的整批問題；`grill-with-docs` 一次一題）。決策歸使用者，不替使用者決定。
- **能查的事實不問。** 來源、`source/`、設計稿 README、`CONTEXT.md` 查得到的就去查（例如設計稿的 JS 實際做了什麼）。
- **依賴順序。** 上游決策先問。某個決策會改變其他問題的前提，就先問它，被它影響的問題等答案出來再決定還要不要問。
- **決策當場落檔**，不要批次到最後：
  - 跨 Goal 的規則 → `user-goal.md` 的「共同前提」
  - 某個流程的行為 → 對應的 Scenario
  - 術語定義 → `CONTEXT.md`
  - 落檔後才算「來源」，才符合「來源沒寫的不自行補」。
- **使用者答「還沒決定」就停止追問**，該項進「來源落差」，標明影響哪幾張卡與暫採的讀法。不要為了問完而逼使用者現場決定。
- **不要在 grill 過程中開卡或估點**，那是 Step 4。

### Step 1 的停止條件

輸入模糊時 grill 到以下全部成立為止：

- 每個 Goal 的「角色／能力／原本的負擔」三格都填得出來，且不是功能清單
- 每個 Feature 可以獨立驗收
- 共同前提沒有懸空的名詞（出現了但沒定義的詞）
- 每個 Feature 至少預期有一個正常與一個被拒絕的情境

不用把所有細節問完。細節留給 Step 2 寫 Scenario 時、Step 3 review 時再問。

### Step 3 的流程

1. 照下面 checklist 掃過**每一條** Scenario。
2. 向使用者報告：有發現的列「Scenario 編號 × 檢查類別 × 問題」；沒發現的合併成一行（例如「其餘 N 條五類皆無發現」）。
3. 把 findings 依依賴順序排成問題隊列，逐題 grill。
4. 解掉的改檔；未決的進來源落差。
5. 使用者確認後才進 Step 4。

## Review checklist（五類）

### 1. 一致性

- Scenario 與「共同前提」不矛盾。
- Goal 標題與底下 Scenario 實際涵蓋的範圍相符（標題說「建立」，Scenario 卻只有「進入」）。
- 來源自己寫的統計數字、清單與實際內容相符。
- 同一件事在不同 Scenario 裡的描述不互相衝突（例如核准者是誰）。

### 2. 完整性

- 有負向 Scenario：憑證／token 過期或已使用、超過次數上限、狀態不允許、重複執行（idempotency）、外部系統不可用、權限不足。
- **前置狀態可達**：每個 Given 描述的狀態，都有某個 Feature（或明確的外部前提）能產生它。
- **實體生命週期**：每個實體的建立、修改、停用、刪除、重設，有沒有哪一段整個不存在。
- 角色邊界清楚：同一件事不會有時寫 A 角色、有時寫 B 角色。
- 權限只寫「具有 XX 權限」時，有對應的權限清單。
- 階段／優先序已標示（來源沒標就留白，列進落差）。

### 3. 合法性（Gherkin）

- 一個 Scenario 一個 `When`（`When … And …` 串兩個動作也算兩個）。
- Then 寫可觀察的結果，不寫操作。
- Given 只放前提，不放動作。
- 沒有 `Or`（不是 Gherkin 關鍵字）。原樣保留來源寫法時，在落差裡註明怎麼改（拆成兩條或 Scenario Outline）。

### 4. 詞彙

- 同一個概念用了多個詞。
- 同一個詞指了多個概念。
- 名詞出現了但沒定義。

### 5. 設計稿（有設計稿時才掃）

- 畫面上的每個區塊／欄位／分頁，有沒有對應的 Scenario；需要畫面的 Scenario，有沒有對應畫面（雙向）。
- 畫面元素的語意是否有定義：這個欄位拿來做什麼、這個分頁和另一個差在哪、這個按鈕點下去去哪。來源沒寫就問，不要從畫面猜。
- 錯誤、受阻、空狀態有沒有畫面與文案。
- 設計稿的做法與「共同前提」有沒有衝突。

## 每個發現的去處

二選一，不要留在對話裡：

- 使用者同意的修正 → 改 `user-goal.md`／`CONTEXT.md`
- 使用者未決 → 記進 `breakdown.md` 的「來源落差」
