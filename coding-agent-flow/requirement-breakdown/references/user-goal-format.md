# `user-goal.md` 骨架

釐清 Goal、撰寫 Scenario 與 review 時的文件格式。BDD 寫在 Scenario 底下，不另開第二個檔案；來源快照放在同層的 `source/` 或沿用既有位置。

有需要獨立維護的術語時放同層 `CONTEXT.md`；「共同前提」放跨 Goal 的規則。簡單且無歧義的名詞不必另建文件。

````markdown
# <主題> — User Goals & BDD

## 共同前提

- <跨所有 Goal 都成立的規則，例如 correlation key、系統職責邊界、正常流程不得做的事>
- <每條都是一句可被 Scenario 引用的斷言>

---

# Goal 1 — <使用者想達成的結果>

**User Goal**

作為<角色>，我希望<能力>，而不需要<原本的負擔>。

## Feature 1.1 — <可獨立驗收的能力>

### Scenario 1.1.1 — <情境名稱>

- **Given** <前提>
- **And** <前提>
- **When** <單一動作>
- **Then** <可觀察的結果>
- **And** <不得發生的事>

### Scenario 1.1.2 — <替代或被拒絕的情境>

- **Given** …
- **When** …
- **Then** …

<一句話收束這個 Feature 的意義，可省略>

---

# Scope Summary

| 階段 | 範圍 |
|---|---|
| P0 | Goal 1、Goal 2… |
| P1 | … |
| Optional | … |
````

## 規則

- 編號連續且穩定：`Goal N` → `Feature N.x` → `Scenario N.x.y`。後面的 `breakdown.md` 與 `cards.json` 直接引用這些編號，改編號等於改追溯鍊。
- 一個 Scenario 一個 `When`。需要兩個動作就拆兩個 Scenario。
- 安全性與不變量寫成 `Then` 的「不得…」，例如「不得建立第二筆帳號」「不得洩漏帳號是否存在」。
- 來源用了 Gherkin 沒有的關鍵字（如 `Or`）時原樣保留，並在「來源落差」註明要改寫成 Scenario Outline 或拆成兩條。
- 階段照來源抄。來源沒把某個 Goal 放進 Scope Summary 就留白，不要自己指派。

# 來源存檔的 `README.md` 骨架

外部來源（文件、wiki／Notion 頁、設計稿）一律先存進 `<主題>/source/` 再拆，否則來源一改，沒有人說得出當初拆的是哪一版。既有的 `design/` 目錄視同 `source/`。

## 非設計稿的來源

````markdown
# <來源名稱> — 來源快照

出處：<URL 或文件位置>
擷取日期：<YYYY-MM-DD>
來源最後修改：<來源頁顯示的時間；沒有就寫「未知」>

## 內容

| 檔案 | 說明 |
|---|---|
| `<檔名>` | <匯出格式（md／html／pdf）、是否經過編輯> |

## 注意

<來源自己的已知問題，例如頁首統計數字與實際內容不符；快照時不修正，原樣保存>
````

快照保持原樣，不修正、不整理。整理的結果寫在 `user-goal.md`。

## 設計稿

設計稿比一般文件多記版面、token 與互動，否則過幾天沒人說得出畫面上原本有什麼。

````markdown
# <頁面名稱> — 設計原件

擷取自 <URL>，擷取日期 <YYYY-MM-DD>。

## 內容

| 檔案 | 說明 |
|---|---|
| `index.html` | 頁面原始碼，與伺服器回傳內容完全一致（未修改） |
| `*.png` | logo、預覽圖、全頁截圖 |

## 頁面結構

<版面、區塊、每個區塊的元素與 data 屬性>

## 互動

<內嵌 JS 實際做了什麼；沒做的事也要寫，例如「點擊只換預覽圖，沒有任何導流行為」>

## 設計 token（取自 `:root`）

```
--paper #f4efe6   --ink #23332e   …
字體：…
```

## 注意

<非原始設計的雜訊，例如 CDN 注入的偵測 script>
````

設計稿衍生的 Goal 給獨立編號（接在來源 Goal 之後），Scenario 只描述畫面上看得到的東西；「這個畫面屬於誰、點下去去哪裡、欄位拿來做什麼」若來源沒寫，寫進「來源落差」，不要從畫面猜。
