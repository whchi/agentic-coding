# 釐清需求與 Review

釐清 Goal 或 review Scenario 時使用。從來源、設計稿、既有決策找答案；只把需要產品決策的缺口交給使用者。

## 釐清與紀錄

- 問題依依賴排序，上游答案會影響下游時先解上游。對獨立問題可一併提出，附可行選項與建議。
- 沿用使用者已確認的答案；不為了走完流程重問。
- 使用者尚未決定的項目停止追問，記入「來源落差」，標明暫採讀法、風險及受影響卡片。
- 規則放 `user-goal.md` 的共同前提；流程行為放 Scenario；需要獨立維護的術語放主題內 `CONTEXT.md`。只有真實且重要的設計取捨才需要 ADR。
- 一般釐清不必啟動另一個 skill。使用者要求深入壓力測試時才考慮 `grilling`；需要對照 repo 證據與術語決策時才考慮 `grill-with-docs`，並沿用主題目錄。

Goal 的角色、能力與原本負擔可說清楚、Feature 可獨立驗收時，即可開始 Scenario。後續細節在寫情境時補，不要求先解完所有問題。

## Review checklist

檢查範圍內每條 Scenario；無發現項目可合併報告。各類只檢查適用條件，不為每條情境硬塞所有負向分支。

| 類別 | 要確認的事 |
| --- | --- |
| 一致性 | Scenario 符合共同前提與 Goal 範圍；相同規則不互相衝突；來源清單與統計可對上 |
| 完整性 | Given 的狀態可達；相關實體生命週期有交代；角色／權限清楚；涵蓋適用的逾時、重複操作、狀態拒絕、外部失敗 |
| Gherkin | 一個 Scenario 一個觸發動作；Given 是前提、Then 是結果；需要不同動作時拆情境；`Or` 不能當關鍵字 |
| 詞彙 | 一詞多義、同義多詞、未定義名詞有處理 |
| 設計稿 | 畫面與情境能互相追溯；欄位、按鈕、分頁語意有來源；錯誤／空／受阻狀態符合規則 |

來源沒有標示階段／優先序就留白。設計稿沒有寫清楚的目的與去向不能靠畫面猜。

## 發現的處理

報告「Scenario 編號 × 問題 × 影響」，再處理會阻擋正確拆解的決策。已授權修改且有來源支持的修正直接落檔；未決項目進 `breakdown.md` 的來源落差。只要求 review 時交付 findings，不自動重寫。

修正與卡片整理可在同次授權範圍內繼續；實際建卡仍需外部寫入授權。
